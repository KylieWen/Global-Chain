# GlobeChain 架构说明

## 当前基线（2026-08-25）

项目已完成最小工程骨架、通用数据契约、mock fixture、只读 fixture loader、领域查询层、无地图 Web 页面，以及 2023 年通用智能手机 published 数据集。国家贸易账本和代表性供应链内容均从本地 active manifest 指向的不可变 release fixture 只读展示；当前仍没有数据库迁移、地图或运行时外部 API。本文既是目标架构，也是后续实现的约束；其中尚未实现的部分必须以代码和测试为准逐步更新。

## 总体决策

采用模块化单体（modular monolith）作为首版部署单元。所有模块可在一个应用仓库和一个部署中协作，但通过清晰的领域边界、接口和数据表分区保持可替换性。只有在容量、团队边界、合规隔离或发布节奏形成真实需求后，才评估拆分服务。

推荐分层如下：

1. **Web 层**：路由、页面、交互状态、图表和可访问性；只消费应用查询接口，不持有业务事实常量。
2. **应用/领域层**：商品、国家、供应链流、贸易账本、指标定义、过滤和跨模块链接的用例与规则。
3. **数据处理层**：导入、清洗、标准化、分类映射、校验、聚合和发布批次；可作为同一仓库中的批处理 CLI/作业运行。
4. **数据库层**：标准维度、发布事实、路线内容、来源、方法和版本记录；供应链流与官方贸易统计分开存储。
5. **内容配置层**：人工编辑的商品简介、路线节点/边、标签、免责声明和导航配置；通过 schema 校验后发布。

## 技术栈状态

- 应用：已初始化 TypeScript + React + Next.js（单一 Web/服务端应用，适合服务端渲染和静态/动态混合）。
- 包管理：已使用 pnpm workspace；首版保持模块化单体，不引入 Turborepo。
- 数据库：目标为 PostgreSQL；当前尚未创建迁移，运行时由 `packages/db` 的只读 fixture loader 提供开发数据。
- 数据处理：Python（pandas/polars + Pydantic）或 TypeScript CLI；优先选择团队已熟悉且便于批量校验的方案，不在 MVP 同时引入两套复杂框架。
- 校验：TypeScript 侧 Zod，数据处理侧 Pydantic/JSON Schema；同一领域 schema 生成或双向测试保持一致。
- 可视化：先采用成熟的 React 图表库；地图能力在确认数据与 UX 后再引入 MapLibre 等库，不为本次文档阶段安装依赖。
- 测试：Vitest/Playwright（或团队已有等价工具）分别覆盖领域规则、查询契约和关键用户流。
- CI：`.github/workflows/ci.yml` 执行 frozen install、active release 校验、类型检查、lint、测试和构建；不在运行时拉取未经审核的外部数据。

Node、pnpm、Next.js、React、TypeScript、ESLint 和 Vitest 的实际版本记录在根目录 `package.json`、锁文件和 README 中。PostgreSQL、Python/uv、地图和图表依赖尚未接入；接入前仍需记录版本、许可证和可替代方案。

## 模块边界

### 商品目录与分类

维护内部商品 ID、名称、门类、别名及外部分类编码映射。手机、功率半导体、汽车等均为普通商品记录，不允许在代码中出现特殊类型枚举分支。

### 国家与地理维度

维护国家/地区稳定 ID、ISO 代码、显示名称和别名。地理层只承载标准化维度，不把地图坐标或国家集合硬编码到页面。

### 供应链内容

维护代表性路线的节点、环节、货物、方向、适用年份/版本、来源和说明。它是内容/示意事实，不是订单或实时物流事实。

### 贸易账本

维护官方或明确标注的统计事实：进口、出口、伙伴、商品结构、顺差/逆差、外汇储备等。每条事实都带统计口径、单位、来源、状态和版本。

### 发布与审计

负责数据批次、内容版本、校验结果、审批/发布状态和回滚指针。Web 层只读取 `published` 版本，预览环境可读取 `draft` 但必须显式标识。

当前实现：`loadFixtureRepositoryFromManifest` 默认只加载 `published`；读取 `draft` 必须显式传入 `allowedStatuses`。`packages/domain` 不依赖文件系统，只依赖只读 `FixtureRepository`，并提供商品目录、拆解树、供应链故事、节点详情、国家账本和 provenance 查询。供应链查询负责解析节点、边、生产活动、步骤、来源、逐条 evidence 和内容版本，Web 页面不得自行连接这些 ID。

### 制造工艺与设备能力

工艺深度层独立维护 `ManufacturingProcessChain`、`ManufacturingRouteVariant`、`ManufacturingProcessStep`、`ProcessRequirement`、`EquipmentCategory`、`Organization`、`Facility` 和 `OrganizationCapability`。路线变体显式保存适用工序，避免把线焊、倒装或未来先进封装误画成一条必经直线。它通过商品 ID 连接供应链层，但不自动生成国家间流向。企业产品或年报只能支持“厂商具备某设备类别能力”；只有明确披露客户、设备、期间和关系的来源才能建立商业供货关系记录。

## 存储分离与连接

供应链和贸易账本使用不同的事实表/逻辑 schema，避免把示意路线误当作海关统计：

- `supply_chain_*`：路线、节点、生产环节、代表性流和内容证据。
- `trade_*`：进口/出口、伙伴、商品结构、宏观指标及统计口径。
- `dim_*`：商品、国家、年份、单位、分类编码等共享标准维度。
- `provenance_*`：数据源、获取批次、转换步骤、校验、方法、数据集版本和发布记录。

供应链层还必须把“证据支持范围”和“金额/数量数据状态”分开：国家角色资料不能被查询或页面自动解释成双边流向；代表性连接必须保持明确标识。

跨模块查询只通过稳定的商品 ID、国家 ID、年份和版本连接；不通过名称模糊匹配或页面临时拼接。

## 数据流

```text
公开来源/人工内容
        |
        v
原始快照（不可变） -> 清洗/标准化 -> 分类映射 -> 规则校验
                                      |
                                      v
                               候选发布批次
                                      |
                               人工复核/批准
                                      |
                                      v
                               published 数据
                                      |
                                      v
                                   Web 查询
```

每一步都记录输入、输出、执行时间、代码/规则版本和操作者或自动作业身份。原始快照与发布事实不混存，便于重跑和审计。

## 配置驱动的扩展方式

新增商品应包含：商品目录记录、分类编码映射、必要的路线内容配置、指标选择和文案。核心页面通过通用查询和渲染组件读取这些配置，不添加 `if (product === ...)` 之类的业务分支。新增国家、年度和伙伴同理。

## 运行时边界

- 运行时只读取已发布数据和内容，不调用 LLM 或生成式服务。
- 计算允许做确定性的过滤、排序、汇总和单位换算；经济结论、利润或因果解释不得由运行时自动生成。
- 对外导出的图表/CSV 应携带数据集版本、内容版本、来源、method 和生成时间。

## 非功能要求

- 可追溯：事实到来源、转换和发布批次可回溯。
- 可重现：同一输入快照、代码和规则版本可重建同一结果。
- 可访问：图表有文本摘要、单位和键盘可达的筛选控件。
- 可观测：记录查询耗时、数据版本、校验失败和发布事件，不记录不必要的个人数据。
- 可回滚：发布以版本指针切换完成，保留上一稳定版本。

## 当前不做的架构工作

不创建地图页面、不接入外部数据、不创建数据库迁移或 PostgreSQL 查询、不实现手机专属页面，也不进行大规模重构。以上属于后续路线图中的独立阶段。loader 与领域查询的详细使用方式见 `docs/phase4-data-access.md`。
